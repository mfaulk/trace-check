# first-check — an insecure and a constant-time tag comparison

A first run of `cargo trace-check` on a crate that knows nothing about this
repository: its own workspace, its own lockfile, registry dependencies only, and
the installed CLI run from this directory.

[`src/lib.rs`](src/lib.rs) has two 16-byte authentication-tag comparisons, both
declared constant-time in `expected`:

| Function | How it compares | Expected outcome |
| --- | --- | --- |
| `tag_eq_insecure` | returns at the first differing byte | `LEAK_DETECTED`, a secret-dependent branch at the comparison line (`src/lib.rs:21`) |
| `tag_eq_ct` | `subtle::ConstantTimeEq` over all 16 bytes | `NO_LEAK_OBSERVED`, calibration and secret binding confirmed |

`tag_eq_insecure` is an analyzer fixture with a planted leak, not code to copy.
[`trace-check.toml`](trace-check.toml) declares it an `analyzer-regression`
expected to produce `LEAK_DETECTED`, so detecting the leak is a pass (exit 0).
`tag_eq_ct` is an ordinary security contract: a leak there would fail with
exit 1.

## Why the insecure version uses `read_volatile`

The obvious early exit, `if expected[i] != supplied[i] { return false }`, does
not leak once compiled. At opt-level 3 the loop is vectorized into a branchless
compare-and-mask, so the honest verdict for that artifact is no secret-dependent
branch, and a demo built on it would prove nothing. Reading each byte with
`core::ptr::read_volatile` keeps the per-byte branch in the machine code.

That depends on the compiler, so CI checks it directly. It disassembles the
executable Memcheck analyzed and fails unless `tag_eq_insecure` still contains a
conditional jump after a byte compare. `--self-test` removes the volatile read
from a copy and confirms the guard then fails.

## Run it

Requirements: Linux x86-64, Valgrind with its client-request headers, a C
compiler, and Rust 1.97 or newer.

Once the crates are on crates.io:

```sh
cargo install cargo-trace-check --locked
cd examples/first-check
cargo test
cargo trace-check check --contract first_check::tag_eq_insecure
cargo trace-check check --contract first_check::tag_eq_ct
```

Until then (#35), `trace-check-test = "=0.1.0"` cannot resolve from the
registry. Run the same steps from the repository root with the script CI uses.
It packages this checkout's release archives, installs the CLI from them into a
temporary root, points a private `CARGO_HOME` at them with `[patch.crates-io]`,
and runs the commands above from this directory:

```sh
python3 ci/verify-first-check.py --self-test
```

The manifest never refers to the checkout. The committed `Cargo.lock` pins
`subtle` and the rest of the graph; its `trace-check-*` entries carry no
registry source while they are served by that patch.

## What CI asserts

`.github/workflows/demos.yml` runs `ci/verify-first-check.py --self-test`, which
reads the JSON report (never the text) and asserts:

- `cargo test`: both functions agree on equal, first-byte-differs,
  last-byte-differs and all-bytes-differ tags.
- `tag_eq_insecure`: exit 0, outcome `LEAK_DETECTED`, policy `satisfied`, a
  finding whose site is the `if byte != supplied[index]` line, calibration and
  binding `confirmed`.
- `tag_eq_ct`: exit 0, outcome `NO_LEAK_OBSERVED` with no findings, at least one
  completed case, calibration and binding `confirmed`.
- The analyzed `tag_eq_insecure` contains a byte compare followed by a
  conditional jump, and the same guard fails on a copy without
  `read_volatile`.

## Claim boundary

A `NO_LEAK_OBSERVED` covers the generated inputs (64 by default) and the paths
they took in one artifact: release profile, `opt-level=3`, `lto=off`,
`codegen-units=1`, built by the toolchain recorded in the report. Memcheck
models secret-dependent branches and addresses, not caches, speculation, or
data-dependent instruction timing. It is not a proof of constant-time behavior.
