# Target selection and source pinning

## The library

[RustCrypto `crypto-bigint`](https://github.com/RustCrypto/crypto-bigint), the
published release `0.7.10`.

`=0.7.10` rather than `0.7.10` is deliberate. Every result this audit records
describes one compiled artifact, so the dependency's exact version is part of
the pinned configuration; a caret requirement would let a patch release change
the code a recorded finding refers to without changing anything in this
repository. The exact-version requirement also makes the mutation experiments
meaningful: the clean reference and the patched copy differ in the patch and in
nothing else.

### On the upstream revision

The M9 plan names `55af01b1957b1f90d718bf697ea9a6db7287151c` as the commit the
`v0.7.10` tag resolves to. That is **not** what this audit pins, and the
distinction matters: the adapter consumes the published crates.io release, and
a registry tarball carries no git metadata, so nothing in this repository can
confirm that a given commit produced it. The tarball checksum above is the pin
that can be verified locally, and it is what the mutation experiments diff
against. Anyone wanting the commit-level correspondence has to compare the
upstream tag's tree against the published tarball themselves.

## Why this library

Three properties, in the order they mattered:

1. **It is somebody else's code.** The point of M9 is to analyze an
   independently developed implementation, so the only acceptable integration
   is one that consumes a published release and does not rewrite it.
2. **Its operations need no general support for Rust generics or custom types
   in `#[constant_time]`.** `Uint<LIMBS>` is reached through functions that
   take and return it; a thin adapter over `&[u8; 32]` can construct one,
   invoke the real operation, and consume the real result. Broadening the
   annotation's type system is an explicit M9 non-goal, and the propagation
   question — whether a declared secret survives the transition from bytes to
   optimized multi-limb arithmetic — would not be answered by accepting `U256`
   as a parameter type anyway.
3. **It is `no_std` and dependency-light.** The analyzed artifact contains the
   arithmetic and little else, which keeps both the disassembly evidence and
   the Memcheck output readable.

## The three operations

| Target | Operation | Why it is here | Input domain |
| --- | --- | --- | --- |
| A | `U256::wrapping_add` | realistic 256-bit representation, carry propagation across machine limbs, straightforward semantics | **total** — defined for every pair of 256-bit values |
| B | `U256`'s `CtSelect::ct_select` | conditional selection is the constant-time idiom cryptographic code is built out of | **total** — any two candidates, any `Choice` |
| C | `ConstMontyForm::mul` with a pinned odd modulus | multi-limb multiplication, Montgomery representation, modular reduction, fixed cryptographic parameters | **total** — see below |

Target A is implemented and analyzed. Targets B and C are M9.2 work.

### Input domains, and the operation that was rejected

The milestone plan singles out `U256::add_mod`, whose documented precondition
is that the unbounded sum of its operands is less than twice the modulus. It is
not a general reduction of arbitrary 256-bit values, so feeding it unrestricted
generated byte arrays would produce behavior that says nothing about valid
cryptographic usage. It is **not** a target here, and no adapter reaches it.

The three chosen operations are all total over their adapters' input types,
which removes the whole class of question:

* `wrapping_add` is addition mod 2^256.
* `ct_select` constrains nothing about its candidates; the adapter's only
  obligation is to build the `Choice` without branching on the secret.
* `ConstMontyForm::new` is a Montgomery multiplication by `R^2 mod p`, which
  reduces its argument — so an arbitrary 256-bit value is a valid input and the
  adapter needs no reduction step of its own, and no rejection branch. This was
  checked against the pinned source
  (`src/modular/const_monty_form.rs:95`), not assumed.

Because every adapter is total, there is no `assume` constraint anywhere in
this example and no input is silently dropped. That is a property of these
three operations, not a general one: an adapter over an operation with a real
precondition would have to document and enforce the restricted domain, and say
so in its report.
