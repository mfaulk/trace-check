# M11.6 — The two external controls

Both controls use published advisories about libraries this project did not
write. Neither can count as a discovery, and the negative one did not come out
the way the plan predicted.

| Control | Advisory | Outcome |
| --- | --- | --- |
| Positive — `rsa` 0.9.10 | RUSTSEC-2023-0071, no patched version | **detected**, in the arithmetic the advisory concerns |
| Negative — `ml-dsa` 0.1.0-rc.2 against 0.1.2 | RUSTSEC-2025-0144, patched in 0.1.0-rc.3 | **unavailable on this platform** — the division is not in the compiled code |

---

## 1. Positive control: `rsa` 0.9.10, the Marvin attack

RUSTSEC-2023-0071 (2023-11-22) says *"information about the private key is
leaked through timing information which is observable over the network"*, lists
**no patched version**, and affects `rsa` 0.9.10 — the latest stable release.
So the control does not depend on pinning something old: the defect is in
current published source.

`examples/rsa-control` analyzes `rsa::BigUint::modpow`, the modular
exponentiation `rsa` 0.9's private-key operations compute with, over a committed
1024-bit modulus. `modpow` is total over both arguments, so generated bytes are
valid inputs and no finding can be an artifact of a violated precondition.

### `modpow_secret_exponent` — `LEAK_DETECTED`

Three findings over 32 cases: one secret-dependent branch and two
secret-dependent value uses, each attributed to the marked exponent. The stacks
name the three places the leak lives:

```text
at normalize (biguint.rs:2391)            # length normalization: the exponent's
at normalized (biguint.rs:2399)           # magnitude decides a branch
at new_native (biguint.rs:2085)

at spilled<[u32; 8]> (src/lib.rs:1082)    # smallvec, reached through the limb
at triple<[u32; 8]> (src/lib.rs:1052)     # vector's own length handling
at len<[u32; 8]> (src/lib.rs:1031)

at num_bigint_dig::biguint::monty::montgomery (src/lib.rs:0)
at monty_modpow (monty.rs:189)            # the Montgomery exponentiation itself
at <num_bigint_dig::biguint::BigUint>::modpow (biguint.rs:2411)
```

That is the control working: a documented, externally reported
secret-dependent operation, found without the tool being told where to look.

### `modpow_secret_base` — `INCONCLUSIVE`, with a real finding inside it

The same exponentiation with the base marked instead reports an **attributed**
secret-dependent branch at the same `normalize` frame, and then declines to
conclude because 25 further undefined-value uses could not be traced to the
marked secret.

Worth stating plainly, because the outcome name alone understates it: the tool
found a genuine leak and still refused to issue a verdict, because unresolved
diagnostics mean it cannot say what else the run did. That is the fail-closed
direction, and it is the same mechanism as the `ml-kem` audit's finding A.

### What the positive control does **not** show

It is not an end-to-end demonstration of the Marvin attack. No padding oracle,
no network, no measurement of how many queries key recovery needs, and no claim
about `rsa`'s higher-level `decrypt`. It establishes one link in that chain —
that the exponentiation's control flow depends on the exponent — which is the
link an observation model of branches and addresses can speak to at all.

## 2. Negative control: `ml-dsa`, and why it is unavailable here

RUSTSEC-2025-0144 (reported 2025-12-12, issued 2026-01-27, CVE-2026-22705)
records that `decompose` performed `r1.0 /= TwoGamma2::U32` — a variable-latency
hardware division — on values derived from the secret `s2` and `t0` during
signing. Patched in 0.1.0-rc.3 by replacing the division with Barrett reduction.

The control was designed to demonstrate a *limit*: division latency is not in
this project's observation model, so a correct run reports nothing, and showing
that is more honest than asserting it. `examples/ml-dsa-control-vulnerable`
(`=0.1.0-rc.2`) and `examples/ml-dsa-control-patched` (`=0.1.2`) compile
**byte-identical contracts** — one `include!`s the other's source — so the two
runs differ in the library version and in a three-line shim that absorbs the
one API change between them.

### Condition 1 fails: the division is not in the artifact

M11's plan fixed the order of work: *first* establish from the disassembly that
a secret-derived operand reaches a hardware division, because a compiler that
strength-reduces the division removes the vulnerability from the artifact and
makes a clean result meaningless. That is what happened.

| | vulnerable 0.1.0-rc.2 | patched 0.1.2 |
| --- | --- | --- |
| `raw_sign_deterministic` | 6444 instructions, **0 `div`** | 3360 instructions, 0 `div` |
| `from_seed` | 2373 instructions, 0 `div` | 1455 instructions, 0 `div` |
| symbols named `decompose`/`high_bits`/`low_bits` | none — fully inlined | none |
| `div` in all `ml_dsa` code | **2** | 0 |
| `div` in the whole artifact | 22 | 20 |

The divisor `TwoGamma2::U32` is a compile-time constant, so at `opt-level = 3`
rustc 1.97 strength-reduces `r1.0 /= TwoGamma2::U32` to a multiply and shift.
The advisory's defect is **not present** in the analyzed machine code.

Two artifacts were examined and agree: the analyzed executable `check` built
(`raw_sign_deterministic` 6444 instructions, no division) and the control
crate's own release `rlib`, which is what `ci/verify-m11-controls.py` reads in
CI (737 instructions, no division — fewer because it has not yet been inlined
into a binary).

The two `div` instructions that *are* in rc.2's `ml_dsa` code are not it. Both
are `256 / stride` in the NTT's loop structure:

```text
cmp    $0x100,%r14
ja     ...
mov    $0x100,%eax
xor    %edx,%edx
div    %r14d
```

`%r14` is a butterfly stride — public structural data, not a secret
coefficient — and both disappear in 0.1.2 because its NTT was rewritten. The
remaining 20 divisions in each artifact are in `std`, `addr2line` and
`rustc_demangle` code that is identical in both.

### So the control is recorded as unavailable, not as a demonstration

Per the plan: *"If condition 1 fails under the pinned toolchain, the control is
recorded as unavailable with the disassembly that shows why, rather than being
presented as a successful demonstration of a limit."*

This is the clearest vindication of that rule the milestone produced. Both
halves return `INCONCLUSIVE` with zero attributed findings, and it would have
been easy — and wrong — to present "same answer for the vulnerable and the
patched version" as a demonstration that trace-check cannot see the advisory's
defect. The honest statement is narrower:

* the advisory's division is absent from both artifacts on Linux x86-64 under
  rustc 1.97 at `opt-level = 3`, so this experiment cannot show whether the
  analysis would miss it;
* the advisory's own text names `UDIV`, an AArch64 instruction, and this project
  is Linux x86-64 only — so the platform where the defect is reachable is one
  the tool does not support;
* the latency blind spot remains **documented and undemonstrated**. It is in
  [`../limitations.md`](../limitations.md) as a scope statement and not as a
  measurement, which is where it was before M11 and where it stays.

### What the two halves did measure

Both return `INCONCLUSIVE` for both contracts, with **no** attributed findings
and large numbers of unattributable diagnostics — 147 and 32 for the vulnerable
half, 71 and 44 for the patched one. The diagnostics concentrate in ML-DSA's
rejection samplers:

```text
66 × ml_dsa::sampling::coeff_from_half_byte
44 × ml_dsa::sampling::rej_bounded_poly
12 × bit_pack<ml_dsa::MlDsa65>
```

That is the `ml-kem` audit's finding A again, in a third library: branches on
values derived from the marked seed through a SHAKE-based sampler, whose origin
Memcheck attributes somewhere other than the client request, so the tool fails
closed instead of attributing them. `ml-dsa` shares the `sha3`/`shake` stack
with `ml-kem`, and `kyberlib` — which has its own Keccak — is the one target
where the same pattern comes back attributed.

The differing diagnostic counts are **not** a security signal and must not be
read as one. They count unattributable Memcheck reports, which depend on
inlining and on which samplers a given corpus drives.

A practical consequence for anyone pointing this tool at ML-DSA: signing is not
currently analyzable to a verdict. Until the provenance gap is closed, every
run fails closed, and a user would see 147 diagnostics rather than either a
clean result or the advisory's defect.
